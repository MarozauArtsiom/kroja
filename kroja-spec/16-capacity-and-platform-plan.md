## 1. Главное ограничение проекта: один мастер

### Суть

Все расчёты в спеке до сих пор исходили из наличия материала. Это неверная модель. **Кожу можно докупить за неделю, руки докупить нельзя.**

Одна обложка — 3–4 часа ручной работы. Один человек при неполной занятости делает 10–20 обложек в месяц. Это жёсткий физический потолок, и он определяет:

- сколько заказов можно принять, не сорвав сроки;
- как быстро растёт срок изготовления при росте спроса;
- в какой момент бизнес обязан либо остановить приём заказов, либо нанимать.

### Почему это опасно именно на старте

Типичный сценарий провала: пост в Instagram выстреливает, прилетает 40 заказов, очередь растягивается на пять месяцев, клиенты требуют возврат, репутация нового бренда сгорает на первой же волне внимания.

Сайт обязан этому препятствовать **до** оплаты, а не после.

### Модель очереди производства

```
capacityPerMonth      — сколько обложек мастер делает в месяц (вводится вручную)
queueOpen             — сколько заказов в статусе queued + in_progress
leadDaysBase          — базовый срок, 5 рабочих дней
leadDaysPerQueueItem  — сколько добавляет каждый заказ в очереди

leadDays = leadDaysBase + ceil(queueOpen / (capacityPerMonth / 20)) * leadDaysPerQueueItem
```

Три режима, зависящих от заполненности очереди:

| Заполненность очереди | Поведение сайта |
|---|---|
| < 60% | Обычный срок: «Ready in 5 working days» |
| 60–100% | Срок растёт честно: «Ready in 18 working days», плюс подпись «Made by one person — the queue is filling up» |
| > 100% | **Приём заказов останавливается.** Вместо кнопки покупки — лист ожидания: «The queue is full. Join the list and we will write when it opens» |

Третий режим — не потеря продажи, а её перенос. Для ремесленного бренда «очередь закрыта» работает как знак ценности, а не как отказ.

### Что нужно от мастера

Один вопрос, добавленный в `14-master-brief.md`, пакет 1: **сколько обложек ты реально можешь сделать за месяц, если параллельно живёшь обычной жизнью.** Не «в теории», а устойчиво, месяц за месяцем.

## 2. Модель остатка кожи

### Почему стандартный инвентарь не подходит

Коммерческие платформы считают остаток в штуках готового товара. У мастера остаток — в площади кожи. Из одной шкуры получается либо ~20 обложек A6, либо ~12 A5. Модель «остаток по варианту» этого не описывает.

### Модель

```ts
// Остаток: одна запись на пару кожа + цвет
interface LeatherStock {
  leather: LeatherCode;
  color: ColorCode;
  areaRemainingDm2: number;   // сколько кожи осталось, дм²
  reservedDm2: number;        // зарезервировано под оплаченные, но не сделанные заказы
  canReorder: boolean;        // можно ли докупить эту кожу
  reorderDays: number;        // за сколько приходит
}

// Расход на одну обложку, с запасом на раскрой (~40%)
const consumptionDm2: Record<SizeCode, number> = {
  a6: 5.2,
  b6: 7.0,
  standard: 7.5,
  a5: 10.0,
};
```

### Расчёт статуса

```
available = areaRemainingDm2 − reservedDm2
maxCovers = floor(available / consumptionDm2[size])

maxCovers ≥ 1                    → in_stock       (срок = базовый)
maxCovers = 0 и canReorder       → made_to_order  (срок = базовый + reorderDays)
maxCovers = 0 и !canReorder      → unavailable    (только лист ожидания)
```

**Ключевое:** это те же три статуса, что уже описаны в `types/config.ts` как `StockStatus`. Функция `getStock()` в `lib/availability.ts` меняет только источник данных — вся логика конфигуратора, матрица совместимости и тосты о подмене цвета продолжают работать без изменений.

### Списание и резерв

| Событие | Действие |
|---|---|
| Заказ оплачен | `reservedDm2 += consumption[size]` |
| Заказ переходит в `in_progress` | `areaRemainingDm2 −= consumption[size]`, `reservedDm2 −= consumption[size]` |
| Заказ отменён до начала работы | `reservedDm2 −= consumption[size]` |
| Мастер закупил кожу | `areaRemainingDm2 +=` вручную в админке |

### Два ограничителя работают вместе

Заказ проходит, только если выполняются оба условия: **есть кожа** и **есть место в очереди**. Срок изготовления берётся как максимум из двух — срока по коже и срока по очереди.

Чаще срабатывать будет очередь, а не кожа. Это нормально и это правильный сигнал.

## 3. Payload: что даёт и когда внедрять

### Что решает

| Проблема | Как решает Payload |
|---|---|
| Наличие кожи правится в git и требует деплоя | Коллекция `leather-stock`, правится в админке |
| Цены и сроки в коде | Глобал `pricing-settings` |
| Тексты лендинга в коде | Коллекции и глобалы с локализацией |
| Нет способа увидеть заказы | Коллекция `orders` со списком, фильтрами и историей |
| Нет статусов производства | Поле `productionStatus`: queued → in_progress → made → shipped → delivered |
| Нет писем клиенту | Хук `afterChange` на смену статуса → письмо |
| Нет учёта очереди | Вычисляемое поле по количеству заказов в работе |

### Когда внедрять

**Не сейчас.** Триггер один: **решение открывать продажи.** До этого Payload не решает ни одной существующей проблемы, а стоимость сопровождения появляется сразу.

Порядок фаз — в `13-next-phases.md`. Payload относится к фазе 4.

### Что понадобится сделать при внедрении

| Этап | Время |
|---|---|
| Установка Payload в существующий Next.js, база | 0,5 дня |
| Коллекции и глобалы, перенос данных из `content/` | 2 дня |
| Переключение `lib/*` на чтение из Payload | 1 день |
| Плагин ecommerce: корзина, заказы, Stripe | 2–3 дня |
| Чекаут с BLIK/P24, адреса, доставка | 3–4 дня |
| **Остаток кожи: коллекция, расход, списание** | 1–1,5 дня |
| **Очередь производства: расчёт, три режима, лист ожидания** | 1,5–2 дня |
| Статусы заказов и письма | 1–2 дня |
| **Итого** | **13–17 дней** |

Подробное обоснование выбора Payload против Medusa — в `15-platform-comparison.md`.

### Известные риски Payload

Плагин ecommerce находится в бете, возможны ломающие изменения. Практические меры:
- зафиксировать версию плагина в `package.json` без диапазона;
- не использовать варианты товара — конфигурация живёт в метаданных позиции, и самая сырая часть плагина обходится стороной;
- доставку, налоги и статусы производства реализовывать своими коллекциями, не ожидая их от плагина.

## 4. Дальше Payload: плагины или отдельный сервис

**Помеченная мысль, требующая решения в будущем.**

Payload закрывает потребности до определённого масштаба. Дальше развилка, и её стоит увидеть заранее, чтобы не оказаться в ней внезапно.

### Развилка

**Вариант A — плагины Payload.** Собственная логика (остаток кожи, очередь, расчёт конфигуратора) оформляется как переиспользуемые плагины в том же приложении: свои коллекции, хуки, компоненты админки. Всё остаётся одним деплоем.

**Вариант B — отдельный сервис производства.** Логика склада и очереди выносится в самостоятельный сервис со своим API и базой. Payload остаётся витриной, контентом и заказами.

### Когда какой

| Признак | Куда идти |
|---|---|
| Логика склада и очереди укладывается в 3–5 коллекций и десяток хуков | Плагины |
| Появляются другие каналы продаж (Etsy, опт), которым нужен тот же остаток | Отдельный сервис |
| Мастеров становится больше одного, у каждого своя очередь и специализация | Отдельный сервис |
| Производство обрастает этапами с датами, исполнителями и браком | Отдельный сервис |
| Нужна интеграция с бухгалтерией или ERP | Отдельный сервис |
| Логика начинает мешать обновлять Payload | Отдельный сервис |

### Что делать сейчас, чтобы развилка была дешёвой

Ничего специального. Достаточно одного правила: **логика склада и очереди живёт в чистых функциях в `lib/`, а не размазана по хукам и компонентам.** Тогда вынос в сервис — это перенос файлов и замена вызовов на HTTP, а не переписывание.

Это же правило уже действует в текущем MVP для `lib/pricing.ts` и `lib/availability.ts`.

## 5. Что делать в коде прямо сейчас

**Ровно одну вещь:** ввести единую точку импорта данных — `lib/data.ts`, который реэкспортирует всё из `content/`. Пятнадцать минут работы.

Зачем: при переезде на Payload меняется один файл, а не импорты в десяти. Никакой дополнительной сложности для текущей разработки это не создаёт.

Задача заведена как **T-025** в `kroja-backlog/TASKS-1-foundation-and-data.md`.

Всё остальное — не трогать. В частности **не делать сейчас**:
- ❌ асинхронные версии функций `lib/*` «на будущее» — это усложнит все компоненты ради выгоды, которая наступит через полгода;
- ❌ абстрактные репозитории и интерфейсы источников данных;
- ❌ пустые коллекции Payload «чтобы потом было»;
- ❌ поля склада и очереди в текущей модели данных.
