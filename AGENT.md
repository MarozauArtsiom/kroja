## Команда /goal

Когда пользователь пишет `/goal`, ты выполняешь цикл ниже. Один вызов `/goal` = одна выполненная задача.

### Цикл

```
1. ОПРЕДЕЛИТЬ
   Прочитать PROGRESS.md (если его нет — создать, текущая задача T-001).
   Взять первую невыполненную задачу.

2. ПРОЧИТАТЬ
   Найти блок задачи в нужном TASKS-файле.
   Прочитать ЦЕЛИКОМ, включая Business, Do NOT и Acceptance.
   Прочитать раздел 0 в BACKLOG.md, если ещё не читал в этой сессии.

3. ОБЪЯВИТЬ
   Написать одной строкой: «T-0XX — <название>. Создаю: <файлы>.»
   Ничего не обсуждать, не предлагать альтернатив, не задавать вопросов.

4. СДЕЛАТЬ
   Выполнить шаги задачи.
   Если в задаче есть блок Code — использовать его дословно.
   Ничего не добавлять сверх написанного.

5. ПРОВЕРИТЬ
   npm run build
   Упало → чинить, вернуться к шагу 5. Не переходить дальше.
   Прогнать чеклист Acceptance пункт за пунктом, честно.

6. ЗАФИКСИРОВАТЬ
   git add -A && git commit -m "T-0XX: <краткое описание>"
   Дописать строку в PROGRESS.md.

7. ОТЧИТАТЬСЯ
   Три строки, не больше:
   ✅ T-0XX выполнена
   Файлы: <список>
   Следующая: T-0YY — <название>

   Остановиться. Ждать следующего /goal.
```

### Условия остановки

Останавливаешься и **спрашиваешь пользователя**, только если:

- сборка падает трижды подряд и ты не понимаешь причину;
- в задаче противоречие, которое нельзя разрешить чтением;
- задача требует файла, которого нет и который не создавался прошлыми задачами.

Во всех остальных случаях — продолжаешь молча.

### Чего в цикле /goal быть не должно

- ❌ вопросов «а не сделать ли лучше»;
- ❌ предложений альтернативной архитектуры;
- ❌ выполнения двух задач за один `/goal`;
- ❌ пропуска задачи, которая кажется необязательной;
- ❌ длинных объяснений — отчёт три строки.

## Железные правила

Нарушение любого из них = задача выполнена неправильно.

### Порядок

1. Задачи выполняются **строго по возрастанию номера**. Пропусков нет.
2. Нумерация не сплошная (после T-025 идёт T-030) — это нормально.
3. Одна задача = один коммит.
4. `npm run build` после каждой задачи. Красная сборка = стоп.

### Что нельзя добавлять

- Пакеты вне списка в `BACKLOG.md`, раздел 1.2. Разрешены только: `next`, `react`, `react-dom`, `zod`, `zustand`, `clsx` и типы.
- CMS, базу данных, Payload, Medusa, авторизацию, админку.
- Фотографии, стоковые изображения, сгенерированные картинки. **В проекте нет ни одного растрового файла.**
- Собственные SVG. Все чертежи готовы в `kroja-svg/`.
- Абстракции «на будущее»: репозитории, интерфейсы источников данных, асинхронные обёртки.
- Тесты, Docker, CI, Storybook.

### Что нельзя менять

- Файлы предыдущих задач, кроме случаев, где задача прямо это предписывает («Подключение к странице»).
- Комментарии-маркеры `{/* SLOT: ... */}` — по ним следующие задачи находят место вставки.
- Значения из `content/*`: цены, размеры, цвета, тексты. Они заданы намеренно.

### Как писать код

| Правило | Значение |
|---|---|
| TypeScript strict | Ни одного `any` |
| Клиентские компоненты | `'use client'` первой строкой |
| Стили | Только Tailwind-классы, только токены из `tailwind.config.ts` |
| Импорты | Абсолютные: `@/lib/data`, `@/components/ui/Button` |
| Данные | Из `@/lib/data`, а не напрямую из `@/content/*` (после T-025) |
| Деньги | Целые числа в грошах: `30000` = 300 zł. Никакой плавающей точки |
| Меры | Миллиметры и граммы. Никаких дюймов и унций |
| Язык кода | Английский. Язык интерфейса — английский |

## Что это за проект (контекст на две минуты)

Сайт бренда кожаных блокнотов ручной работы KROJA. Три страницы:

| Маршрут | Что это |
|---|---|
| `/` | Продающий лендинг. Должен выглядеть как работающий магазин |
| `/configurator` | Конструктор блокнота: размер, кожа, цвет, нить, шнур, гравировка, вкладыши |
| `/shotlist` | Служебная страница со списком кадров для будущей фотосъёмки |

Плюс корзина — выдвижная панель. **Оплаты нет.** Корзина заканчивается формой резерва конфигурации по email.

**Главная особенность:** фотографий продукта не существует и не будет. Вместо них — схематические SVG-чертежи, которые заодно объясняют мастеру, что нужно сфотографировать в будущем. Не пытайся это «починить» добавлением картинок.

**Ключевое техническое правило проекта:** размер блокнота **не входит** в имя файла превью. Одна фотография покрывает все четыре размера, а масштаб показывается отдельной SVG-схемой. Если тебе захочется добавить размер в ключ — не надо.
